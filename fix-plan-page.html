Allied Priority Fix Plan

Implementation plan for the six client priorities, rebuilt around a stocktake-anchored stock ledger — plus one blocking defect found while verifying the numbers.

Revised 18 Aug 2026 Status P0 shipped · P1–P6 proposed Verified against Live MYOB file, 3,100 items

What changed in v2

  • P1 is rewritten. Stock on hand now comes from a stocktake-anchored ledger, not MYOB's QuantityOnHand. This is the client's direction, and the data supports it.
  • P3 is clarified — yes, we start persisting data now. The plan states exactly which dates will be exact, which reconstructed, and which unreliable.
  • Client answers folded in — no finish suppression, bin location synced but hidden, Allied tags their own suppliers, the "open POs netted" item dropped.
  • P0 has shipped. The sync no longer serves stale quantities, and MYOB's Bill of Materials was verified as genuinely maintained and promoted to the primary recipe source.

The blocker is fixed

A defect sat underneath everything and silently corrupted every quantity in the product. It was invisible from the UI — the numbers looked plausible, they were just old. N12S16 read 299 units against a real 18,449.

Shipped 18 Aug 2026. Stock quantities are now re-read in full on every sync, and staleness is reported as a fault rather than rendered silently. Details in P0 below.

1.3  Bill of Materials — a real endpoint exists Major find

Source: Bill of Materials

GET /Inventory/Item/?$expand=BillOfMaterials returns each item's real recipe — component Item.UID, Item.Number and Quantity — and explicitly covers auto-build items. This supplies P1's kit-component and auto-build verification sample, and largely retires the planned Phase 4 CSV bulk-import: we pull the real BOM rather than asking Allied to hand-key ~1,000 relationships.

1.4  Per-location stock is available

LocationDetails returns { Location, QuantityOnHand } per item. PLAN.md records the per-location split as a documented limitation. That is wrong; it is exposed. Not scheduled, but the note should be corrected.

1.5  Historical data — what the API will and will not give us

There is no as-at inventory endpoint. The Report collection holds only Payroll Advice, Payroll Category Summary, Tax Code Summary, Transaction Coding Summary, Profit and Loss Summary, NZ GST and Balance Sheet Summary. No inventory report, no stock-on-hand-as-at, no per-item trial balance. The item master is present-tense only — no history, no as-at parameter on any quantity or cost field.

Transaction history is fully available by date range. Every transactional endpoint accepts an OData $filter on Date. Our store starts at 2025-08-07 only because SYNC_WINDOW_DAYS is 365 — a self-imposed limit, not an API one. This is what makes backdating possible.

GeneralLedger/JournalTransaction is not a shortcut — it covers Inventory journals and has a UnitCount field, but posts at account level, not item level.

Conclusion: every historical stock figure must be computed by us from a movement ledger. P1 defines that ledger; P3 defines how far back it is trustworthy.

1.6  Stocktakes in MYOB — how they actually appear New research

Driven by the client's direction. Three findings shape the whole design.

Finding 1 — an adjustment records a delta, not a counted quantity

Allied's own memo gives it away: "N8S16 COUNT QTY 66 … QTY 919 ADDED AT STOCK". The line quantity is +919 (the correction); the counted figure 66 survives only as free text. A count adjustment never hands us an absolute — the counted quantity must be recovered as the running balance immediately after the adjustment.

Finding 2 — stocktakes are rolling and partial, identified only by free-text memo. Across the two-year window there are 1,314 adjustments; 51 match stocktake wording, covering 1–24 items each. A sample:

Wording is inconsistent — "Stock Count", "Stocktake", "STOCK TAKE", "COUNT QTY". A regex finds 51 with strict wording but 159 matching "count" loosely, so memo matching can propose candidates but must never silently define truth. Allied confirms each one.

Finding 3 — the ledger is sound, and it proves why anchoring is right. I tested reconstruction by anchoring on the 12 Aug full sync (3,047 items were accurate at that moment) and rolling movements backwards:

Out of 3,047 items, at most 2 fail at any horizon. Bills, invoices, builds and adjustments account for virtually all stock movement across a full year — our movement model is essentially complete.

And the one real failure is the whole argument for the client's model

SPWD20G (M20 double coil spring washer) holds 27,880 at the anchor but reconstructs to −5,080 at 30 June. The intervening window contains a stock-count adjustment. Rolling backwards through a count is invalid — the count absorbed accumulated drift that no document explains. Rolling forwards from a count is exactly right. That is precisely the model Allied asked for, and it becomes a hard rule in the engine.

The work

P0 Stock quantities are stale. Fix the sync first. Shipped 18 Aug

Not in the client's list · Invalidated everything downstream · Went first

MYOB does not update Item.LastModified when a transaction changes an item's quantity — it moves only when the item record itself is edited. Our sync filters LastModified gt <high-water mark>, so items whose stock moved are never re-fetched.

Evidence from the live file

  • 177 inventoried items had stock movement after 12 Aug. Only 14 had an updated item record — 163 carried stale quantities.
  • 2,978 of 3,061 inventoried items share a last_modified of 6–7 May 2026 (a bulk edit).
  • Every incremental run since 12 Aug fetched 2–13 items and reported success while the file drifted.
  • N12S16: we hold qty_on_hand = 299. A bill for 20,000 units landed 13 Aug. Real on-hand ≈ 20,299 — off by 98.5%.

Build

  1. Always fully refresh the items entity. Never LastModified-filter it — ~3,100 rows / ~8 pages, a few seconds. Keep incremental filtering for transactional entities, where MYOB does maintain it.
  2. Pull $expand=BillOfMaterials in the same pass into a new myob_item_bom table.
  3. Persist CustomList1/2/3 and LocationDetails as real columns.
  4. Staleness guard: record quantities_as_of per item, surface it on Data & Sync, and raise a visible error if any item's quantities predate the last completed sync.
  5. Backfill history to the depth set in P3 — the ledger cannot pre-date the transaction data.

P1 Stocktake-anchored stock ledger Rewritten

Depends on P0 · Replaces the previous P1 · This is now the core of the product

"Whenever there is a stock count and they have this in MYOB, that is the reference point. All future numbers should be sales, stock movements, new stock in, etc. adjusted based on that reference point, until the next time they do a stock take."

We no longer read QuantityOnHand as truth. We compute it.

The math

For item i and date D:

Anchor. A(i,D) = (tₐ, qₐ) — the most recent trusted physical count at or before D.

#Anchor sourceTrustHow qₐ is obtained
1Allied-entered count (UI or CSV)HighestEntered directly as an absolute
2MYOB adjustment confirmed as a stocktakeHighRunning balance immediately after the adjustment
3No count on recordLow — labelledEpoch baseline back-computed from the earliest reliable snapshot

Movement ledger. M(i, t₁, t₂] = stock-moving document lines dated in (t₁, t₂]:

M = + purchase bill lines   (received; supplier credits negative → net out)
    − sale invoice lines    (shipped; customer credits negative → add back)
    ± build lines           (positive = produced, negative = consumed)
    ± adjustment lines      EXCLUDING the anchor adjustment itself

That exclusion matters: the count adjustment is already baked into qₐ. Counting it again double-applies the correction.

on_hand(i, D)   = qₐ + M(i, tₐ, D]

committed(i, D) = Σ sale-order line qty where
                    order.date ≤ D
                    AND still open at D (not invoiced, or invoice.date > D)

free(i, D)      = on_hand(i, D) − committed(i, D)
incoming(i, D)  = Σ open PO line qty not yet billed at D

divergence(i)   = on_hand_ledger(i, today) − myob_qty_on_hand(i)

Committed is derived independently and is unaffected by the anchor — it is forward-looking demand, not stock history. MYOB's QuantityAvailable stays visible as a labelled fact and is never used in analysis, because it includes on-order.

Hard rules, derived from the data

  1. Never roll the ledger backwards through a count. For D < tₐ, fall back to the previous anchor. Proven by SPWD20G.
  2. Adjustments are deltas, not counts. Recovering qₐ needs the running balance at that moment.
  3. Exclude the anchor adjustment from the movement sum.
  4. Memo matching proposes, Allied confirms. No regex silently defines an anchor.

An honest word on "trusting us more than MYOB"

A complete ledger and MYOB compute on-hand the same way — by applying every transaction. So the ledger will usually agree with MYOB, and it should. Where it earns more trust is in four specific places, and these are the deliverable:

  1. It is anchored to physical reality. After each count, accumulated drift is wiped. MYOB carries error forward silently until someone notices.
  2. Every number shows its working — anchor, anchor date, and every document since, as a drillable audit trail. MYOB shows a figure with no derivation.
  3. Divergence is detected and priced. Where we disagree with MYOB we say so, quantify it in dollars, and show which documents explain the gap. This is what will actually catch the double debit/credit PO-receipt artefact the brief warns about.
  4. Allied's own counts can override MYOB entirely. If they counted something and never entered it, our number reflects reality and MYOB's does not.

Worth setting this expectation directly with the client: the goal is not a different number, it is a number they can audit — plus the ability to override MYOB with their own counts. Promising "different and better" would be dishonest; "auditable, anchored and correctable" is exactly what we can deliver.

Build

  1. platform_stock_count — (item_uid, count_date, counted_qty, source, source_ref, entered_by, note), source ∈ myob_adjustment | manual | csv_import.
  2. Stocktake detection. Scan adjustment memos for count wording and present candidates on a "Confirm stocktakes" screen — date, memo, affected items, delta, resulting post-adjustment balance. Allied confirms or rejects each. Show the free-text counted quantities from the memo as a cross-check hint, displayed but never parsed as authoritative.
  3. Manual + CSV count entry, so Allied can anchor items MYOB never had a count for. This is the path to genuinely beating MYOB.
  4. Ledger engine implementing the math above, materialised per item per day for speed, rebuildable from scratch.
  5. Divergence panel — every item where ledger ≠ MYOB, ranked by dollar impact, audit trail beside it.
  6. Audit trail UI — click any on-hand figure to see the anchor, then every document since with a running balance.
  7. Coverage metric — how many items are anchored to a real count vs a back-computed baseline, and how old each anchor is. This tells Allied where to count next.

Done when

  • On hand, committed and free stock are each computed by us, each with a visible derivation.
  • Every item shows its anchor, anchor date, source and days since.
  • The divergence panel is empty, or every entry has a documented explanation.
  • Reconciles against Allied's manual month-end for a sample including open POs (122 available), kit components, auto-built items, supplier credits (8 negative bill lines), and at least one item covered by a recent rolling stocktake.
  • SPWD20G produces a correct on-hand figure from its post-count anchor.

P2 Value stock at average cost Cheapest win

Depends on P0 and P1

MYOB gives us the answer directly: CurrentValue = QuantityOnHand × AverageCost for 3,058 of 3,061 items. We do not need to derive valuation from POs and sales at all.

  • Stock value = on_hand × average_cost, where on_hand is now the P1 ledger figure, not MYOB's.
  • Delete the PO/sales-derived valuation path entirely.
  • Apply consistently: item view, inventory list, aggregate totals, every export.
  • Investigate the 3 items where CurrentValue ≠ OnHand × AverageCost.
  • Reconcile the aggregate against MYOB's average-cost valuation report, expecting a documented difference wherever the ledger diverges.

P3 Point-in-time date vs rolling window Hard deadline

Depends on P0 and P1 · Tied to the August inventory run

Direct answer: yes, we start saving data

From the moment P3 ships we persist an immutable daily record, so any date from then on is an exact read rather than a reconstruction, and any window can be selected over it. Three things get stored:

  1. platform_item_snapshot — (as_at_date, item_uid, on_hand, committed, on_order, average_cost), written once per day per item, never mutated.
  2. The full movement ledger from P1, retained permanently — this is what lets any historical date be recomputed and audited, not merely read.
  3. platform_stock_count — every anchor, permanently.

Confidence tiers — what is exact and what is not

TierDate rangeBasisLabel in UI
CountedAny date after a confirmed stocktake for that itemAnchor + documents since"Anchored to count of dd mmm"
SnapshotFrom P3 go-live onwardStored daily snapshot"Snapshot"
ReconstructedBefore go-live, after the item's last anchorLedger rolled from anchor"Reconstructed from n movements"
UnreliableBefore the item's earliest anchorBack-computed baseline"No count on record — indicative only"

31 July 2026 will always be reconstructed — no snapshot existed then. That is fine and it is accurate, but it must be labelled honestly for the August run.

Build

  1. Two visually and functionally distinct controls: an as-at date (default: most recent month end) governing stock position, and a rolling window (default: 6 months, down from 12) governing sales, consumption and demand.
  2. All derived metrics — weekly demand, weeks of cover, below-minimum flags, purchasing suggestions — respect the selected window. Today it is hard-coded at 90/365 days throughout queries.ts; it becomes a parameter.
  3. Committed as-at. Spike first: does Sale/Invoice/Item reference the originating Sale/Order? If yes, an order was open on D when order.date ≤ D < invoice.date. If not, show as-at on hand only, say plainly that committed cannot be reconstructed before snapshots began, and do not fabricate it.
  4. Average cost as-at uses today's average cost against historical quantity, explicitly labelled an approximation. MYOB exposes no cost history.
  5. Validation control: check whether Report/BalanceSheetSummary accepts an as-at date — if so it gives an independent inventory-asset control total. 30-minute spike.

Backdating — how far, and how

Recommendation: pull transaction history back to 1 July 2024 (two years). It spans at least two of Allied's rolling stocktake cycles, so most items get a real anchor rather than a back-computed baseline; it comfortably covers the 6- and 12-month windows; and it is bounded enough to backfill in one run. Going further adds little — anchors older than a cycle are superseded anyway.

  1. Raise SYNC_WINDOW_DAYS and run a one-off deep sync with $filter Date ge datetime'2024-07-01' across bills, invoices, sale orders, purchase orders, builds and adjustments. Ordinary paging, just more pages.
  2. Back-compute the epoch baseline: epoch_qty = on_hand(12 Aug 2026 snapshot) − M(i, epoch, 12 Aug 2026]. The 12 Aug full sync is the only point where MYOB quantities are known-good for all 3,047 items, so it is the pivot. Label the result "no count on record — indicative only".
  3. Run the ledger forward from the epoch. Every confirmed stocktake re-anchors and wipes accumulated error, so early-period uncertainty does not propagate past the first count.
  4. Re-run the completeness check over the deeper history. Any item reconstructing negative between two anchors indicates either a missing document type or an unconfirmed stocktake — both worth chasing.

Not building

No prior-year or two-year comparison view. Declined by the client.

P4 Independent facets plus free-text tags

Depends on P0 · Simplified by client direction — no suppression work

  1. product_type and product_finish as independent filterable, sortable columns. Never concatenated. No compound categories anywhere.
  2. Show every value that exists, including ZINC PLATED, OTHER, BRASS and blank. Allied filters for themselves — no hardcoded allow-list, no hidden values, no standing maintenance burden.
  3. Blank finish or type renders as an explicit "(not set)" facet, so those 113 and 53 items stay reachable rather than vanishing from filters.
  4. Free-text tags — new platform_item_tags (item_uid, tag), many per item, user-created, filterable. This is also how "never require new item codes" is honoured.
  5. Bin location (CustomList3) synced and stored but surfaced nowhere yet, per client direction. Available the moment they want it.
  6. Filter state lives in the URL so a view like "stainless washers" is shareable.

P5 + P6 The purchasing cart Largest item

Build as one piece of work · P6 cannot be fixed inside the current design

P5's editable quantities need the same persistence P6's split-orders need. Doing them separately means building the cart twice.

Why the current design cannot be patched

purchasing() in src/insights/queries.ts:1110 is a stateless recomputation, not a cart:

  • Line 1121 buckets every item under exactly one key — item.supplierName. One item, one bucket, by construction. This is the P6 defect.
  • The key is the supplier name, not UID. Same-named suppliers silently merge; everything unresolved collapses into one "No known supplier" group.
  • There is no cart table anywhere. Nothing persists, so there is nowhere to put an edited quantity, a removal, a supplier choice or a split.
  • platform_item_suppliers holds exactly one row across the entire database — the feature has never run against real data.

Build — four stages

Stage 1 — fan-out (fixes the defect). Group by supplier UID, emitting one line per (item × tagged supplier), so an item with three suppliers appears in all three buckets. Effective supplier becomes the default selection, not the only option. Adding or removing a supplier reflects immediately.

Stage 2 — a real cart. New platform_purchase_cart (item_uid, supplier_uid, qty, state, updated_at) with state ∈ suggested | edited | removed | selected | split.

Stage 3 — double-order protection, all five guard rails.

  1. Badge on every multi-supplier line, in every bucket — "also under 2 other suppliers", visible without hovering.
  2. Linked view — all suppliers for that item side by side with lead time, last/average cost, on-hand and incoming.
  3. Select-one — pick a supplier, the item drops out of the others in a single action.
  4. Explicit split — total plus per-supplier split shown together, so it reads as intentional.
  5. Pre-export check — flag any item still under multiple suppliers with no explicit split.

Stage 4 — export. Real .xlsx per supplier, formatted to paste straight into an email, with reasoning columns travelling on each line.

Not building

No automatic sending of purchase order emails. Rejected by the client as too risky.

Prerequisite — Allied tags their own items

Per client direction, Allied will tag multi-supplier items themselves. Two consequences: stages 1–3 cannot be demonstrated until some items are tagged, so we should ask for a starter set of ~20 items with 2+ suppliers each, ideally including stainless lines, before the demo. Meanwhile we build a throwaway seeded fixture for our own testing, so development is not blocked waiting on them.
